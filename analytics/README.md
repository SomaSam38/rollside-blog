# Direct Google Search Console reporting

This optional cloud-only reader calls Google's Search Console API using Claude's cloud proxy for Google authentication. It has no third-party analytics provider, write API, website visitor tracking script or report storage. The public repository contains code only. Never commit a service-account key, API response, private search queries or performance report.

## One-time owner setup

1. Verify `https://rollside.studio/` in Google Search Console (or the `sc-domain:rollside.studio` domain property). The currently signed-in owner's existing Soma properties are unrelated.
2. In a Google Cloud project, enable the **Google Search Console API**. Create a dedicated `rollside-search-reader` service account with **no project IAM roles and no domain-wide delegation**. It needs no access to Firebase or other websites.
3. In the verified Rollside property's Settings > Users and permissions, add only that service-account email with **Restricted** permission. Search Analytics supports restricted/read access. Do not grant owner access. If an organisation policy prevents service-account keys, stop and use an approved identity mechanism rather than weaken the policy.
4. Create its JSON key and store it only as a private **network secret** of type **GCP access token (with Service Account Key)** in Claude's dedicated **Rollside blog publishing** cloud environment. Allowed website: `www.googleapis.com`. Path prefix: `/webmasters/v3/sites/`. Scopes: `https://www.googleapis.com/auth/webmasters.readonly`. Leave Subject blank. The proxy mints short-lived tokens; the agent never sees the key. Never paste credentials into chat, the task instructions, Git, or terminal output. Keep `GSC_PROPERTY=https://rollside.studio/` as a non-secret environment variable (or the verified domain-property identifier).
5. The network secret creates a narrowly scoped API allow rule. Keep the environment's existing limited network domains; no broad internet access is needed. Keep all unrelated connectors disabled. Run the cloud credential check and report before calling the integration connected. A local run does not prove Mac-independent access.

## Weekly cloud use

`npm test --prefix analytics`, then `npm run report --prefix analytics`. No packages need installing. Local execution without the cloud proxy is expected to return an authentication error. The report goes only to the private cloud session's stdout, not a file or Git commit. Do not echo environment variables, raw auth errors or credentials. Output has two adjacent 28-day windows, ending three Pacific calendar days before execution, using final web-search data. There are eight bounded API queries: blog totals, pages, queries and page/query pairs for each period, at most 1,000 rows per query. Top-row limits and anonymised queries mean query rows do not sum to complete traffic. No data is a valid result; HTTP access failure is a connection failure.

Use the data to adjust **future** briefs when there is enough evidence: expand useful intents gaining impressions, investigate relevant queries with impressions but weak CTR, and prevent multiple posts competing for the same intent. Preserve variety and readable copy. Consider page age, absolute counts and comparable periods; do not call a new post a failure or treat small percentage changes as proof. Search clicks are not conversions or all visits. Keep the reasoning and measurements in the private cloud run. Publish only the resulting article and feed; do not expose reports or change old posts. If authentication or data is unavailable, state that clearly and continue the existing editorial queue without pretending it is data-driven.

Official references: [Google authorization](https://developers.google.com/webmaster-tools/v1/how-tos/authorizing), [Search Analytics API](https://developers.google.com/webmaster-tools/v1/searchanalytics/query), [service accounts](https://developers.google.com/identity/protocols/oauth2/service-account).
